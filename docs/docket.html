EXHIBIT 00

The charge

Most entries to this track will train a model to say fraud or not fraud, report an accuracy number, and call it finished. That number means nothing to a merchant. A merchant's ledger doesn't have an accuracy line — it has profit and loss, denominated in rupees: fraud that slips through, a chargeback fee, a processing fee that's never refunded, and — the line everyone forgets — a genuine customer wrongly declined, who does not come back.

So Arbiter does not output a label. For every payment it renders a verdict — allow, step‑up, or block — chosen by whichever option loses the fewest actual rupees, with the reasoning behind it written down, explainable, and replayable.

EXHIBIT 01

The record

Every foundational choice, and why it survives the obvious follow-up question.

Track
02 — AI Risk Manager

Rated on fit, not prestige. The one skill actually strongest here is ML, and Razorpay's own track note calls this the one that "surfaces the risk and ML minded builders the others miss" — the least crowded of five.

Dataset
A real dataset, not invented data

Real merchant data is impossible to get (private, regulated). Self-generated fraud means writing the exam and the answer key — any accuracy claim would be worthless. Only a real, independently-labelled dataset survives a skeptical panel.

Which one
IEEE-CIS Fraud Detection

590,540 real transactions, ~3.5% fraud. Chosen over the other well-known option specifically because its columns are readable — card type, email domain, device — not scrambled for privacy. You cannot explain a decision you cannot read.

The split
By time. Never at random.

Train on the first 120 days, tune on the next 30, touch the final month exactly once. A gateway deciding today's payment has never seen tomorrow's data — so neither does this, even while learning.

Where AI sits
Numbers by machine learning, words by language model

Deciding allow/step-up/block is a numbers problem — put to a real head-to-head test in Exhibit 07, not assumed. Explaining why, in a sentence a reviewer reads in three seconds, is a language problem. The rule that separates them: the language model never gets a vote.

The docket

BASELINE

First model, first dead end

scope cut

A deliberately plain baseline beat random guessing by 15.8× before any engineering — real signal, confirmed early. Then tried the winning Kaggle team's identity-matching trick: figure out which rows belong to the same real customer. Their reported purity was almost perfect. Eight tested key combinations later, ours wasn't — not close. Investigated to a pre-committed stop threshold, then dropped it, rather than force a shaky number into the story.

FEATURES

Teaching it a customer's past — without cheating

honest wash

Built nine signals from each client's prior transactions only — proved it by hand-recomputing 300 random rows, zero mismatches. Caught, and fixed, one signal that would have quietly used a customer's future transactions — the exact leak this entire project exists to catch, almost shipped in its own code.

TUNING

Trimmed, tuned, then caught its own probabilities lying

two real wins

Cut 339 near-duplicate columns to 279 with no loss. An automated 60-trial search beat hand-picked settings. Then: the standard calibration technique quietly collapsed 91,271 distinct scores down to 323, blurring together transactions the model could tell apart. Caught because the drop was too large to be noise; a gentler method fixed the probabilities without touching the ranking at all.

ENGINE

Left Kaggle. Found the project's worst bug.

13 / 13

Built the real, standalone engine — CPU only, no GPU, no notebook. Then, moving to a clean environment: the model library's local version differed from Kaggle's training version. Same input, two versions, one said 17% fraud probability, the other said 0.7% — a 23× difference, silently, no error at all. Fixed with a hard version pin, plus a runtime guard that refuses to score on any future mismatch — then deliberately broke the guard to confirm it actually fires.

EXHIBIT 05

Two things worth understanding

Why two different accuracy numbers get reported

PR-AUC asks: of what got flagged, how much really was fraud — and of all real fraud, how much got caught. ROC-AUC asks a gentler question flattered by the fact that fraud is rare; a model can score well on it while still wrongly blocking a large share of the customers it touches, and the number wouldn't show it.

Tuned on PR-AUC, the harder one to fool. ROC-AUC reported for context only.

random guess → PR-AUC ≈ 0.035

Why "no peeking at the future" is the whole argument

A gateway decides now, with zero knowledge of what a customer does next. Any technique quietly using later transactions to help score an earlier one looks brilliant in testing and fails the moment it meets production — because in production, later hasn't happened yet.

This is the leaderboard-winning solution's actual mechanism, used on purpose in a file that's already sitting on disk. Exhibit 07 builds the honest version and the cheating version side by side and prices the difference: about 1%. Honesty is nearly free here.

EXHIBIT 06

Would you trust it

A notebook cannot demonstrate this. A standalone, CPU-only program was built and then broken on purpose, six separate ways, to prove each failure recovers rather than assuming it would.

MODEL FILE MISSING OR CORRUPT
Fails closed to a conservative rule, never silently allows. Verified by deleting the artifact mid-test.
MODEL LIBRARY VERSION MISMATCH
Refuses to score at all rather than silently guess. Verified by deliberately faking a mismatch and confirming the refusal fires.
LLM UNAVAILABLE, TIMES OUT, OR RETURNS GARBAGE
The verdict is unaffected — only the prose degrades to a template. Verified by killing the LLM path and diffing the decisions.
REQUIRED FEATURE MISSING
Widens the step-up band rather than guess. The first design for this was proven, on paper, mathematically incapable of moving anything — rebuilt, then verified the boundary actually moved.
DUPLICATE / REPLAYED TRANSACTION ID
Returns the original verdict, unchanged. Verified: same ID submitted twice, byte-identical result.
A STORED RECORD IS TAMPERED WITH
Re-derives the verdict from its own stored inputs and flags the mismatch — the record is provably honest, not just claimed to be.

17 real bugs caught this way across the build, every one logged as it was found, none of them shipped.

EXHIBIT 10

Entered into the record, plainly

Borrows heavily from the 1st-place IEEE-CIS solution, and says so. Taken: the identity-key construction, card-level chargeback label semantics, group aggregates as features, time-consistency screening, and the "unseen clients, not time drift" diagnosis. Diverged, deliberately: causal aggregates instead of full-history ones, no future-leaking post-processing, a cost-minimizing objective instead of an AUC-maximizing one, and a three-way verdict instead of a score. Their model wins the raw Kaggle task, by design — different games, see Exhibit 07.

What it still can't do, stated rather than buried: card-level identity reconstruction was attempted and scoped out, not solved. Step-up outcomes are modeled from cited industry rates, not measured on this dataset — quantified at 0.05% of the headline, not hidden. Built on US card-not-present data; the method transfers to Razorpay's UPI-heavy mix, the specific features would need to be re-derived. Full account: the eval report and the docket in the repository.
