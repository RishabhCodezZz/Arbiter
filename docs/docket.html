EXHIBIT 00

The charge

Fraud decisions involve losses from missed fraud and genuine payments wrongly declined. Arbiter compares assumed margin, processing fees, chargeback fees and customer-loss penalties in an illustrative INR scenario.

For each payment, the policy chooses allow, step‑up or block by maximum expected scenario value. Stored inputs support policy replay; SHAP and optional narrative explain scored flagged cases. Simulated value is not observed merchant profit.

EXHIBIT 01

The record

The initial choices and their limits.

Track
Fraud decisions

The builder chose fraud to work with their ML experience and evaluate decisions against labeled transactions.

Dataset
Labeled transaction data

IEEE-CIS provided observed transaction labels for retrospective evaluation. No private merchant dataset was available for this build.

Which one
IEEE-CIS Fraud Detection

590,540 transactions, about 3.5% fraud. The dataset includes readable fields such as card type, email domain and device, alongside anonymized features.

The split
Temporal split, reused holdout

Train on the first 120 days, tune on the next 30, evaluate on day > 150. The final month was reused for diagnostics, comparisons and selection decisions. Causal features prevent future-row access, but adaptive test feedback still limits independence. A fresh untouched month remains necessary.

Where AI sits
Models score; the policy decides; the LLM writes

The policy selects the action before narrative generation. The historical benchmark in Exhibit 08 compares one scoring model with one LLM on a small sample. It does not establish that every LLM is unsuitable for fraud scoring.

EXHIBIT 05

Two things worth understanding

Precision-recall and ROC measure ranking

Precision measures fraud share among flagged rows; recall measures the share of fraud flagged. PR-AUC summarizes that trade-off across cutoffs. ROC-AUC measures true-positive versus false-positive rates and supplies ranking context, but does not express merchant costs.

Tuning used validation PR-AUC. Current three-way policy counts and the two-way presentation proxy use different decision rules.

random guess → PR-AUC ≈ 0.035

Causal features and independent evaluation

A gateway scoring a payment can use prior transactions, but later rows are unavailable. Full-history aggregates and future client-mean post-processing can therefore leak information into retrospective scores.

Exhibit 08 retains a historical V2 comparison of these techniques. The PR-AUC gaps were +0.0251 for features alone and +0.0066 after post-processing. They apply to this model, features and split, not a universal cost of causal correctness. The reused test month remains a separate evaluation limitation.

EXHIBIT 06

Would you trust it

Historical failure tests exercised the standalone CPU engine. Current fallback behavior and persistence limits are detailed in the architecture.

MODEL FILE MISSING OR CORRUPT
Uses a step-up rules fallback with no calibrated probability. Historical tests removed or corrupted artifacts.
MODEL LIBRARY VERSION MISMATCH
Rejects model scoring and uses the engine's rules fallback. Deliberate mismatch tests exercised the guard.
LLM UNAVAILABLE, TIMES OUT, OR RETURNS GARBAGE
Uses template prose and preserves the selected action. Historical tests disabled the narrative path and compared decisions.
FEATURE CONSTRUCTION FAILS
Tries degraded features, records the fallback and shrinks the scored probability toward 0.5. If both builders fail, uses the step-up rules fallback.
DUPLICATE / REPLAYED TRANSACTION ID
Returns the stored decision without another append. Replay metadata changes: idempotent_replay is true and latency_ms is zero.
A STORED RECORD IS TAMPERED WITH
Checks available hashes and recomputes policy output from stored inputs. Unkeyed hashes can be forged by a writer who recomputes them; replay does not rerun model inference.

Historical testing and automated review found silent version, feature and numeric-validation defects. The journal retains the full repair sequence.

23× · silent
The same input, two different answers

Moving to a clean environment exposed a 23× probability difference on the same input under different model-library versions. A version pin and runtime guard were added; deliberate mismatch tests exercised the guard.

Train ≠ serve
One feature, two different divisors

Automated review found that the engine and training pipeline computed a spread feature with different divisors. For history [0, 2], the values were 1.0 versus 1.4142. The engine was corrected and a parity test added.

Silent allow
A numeric guard accepted NaN

A later review found that the earlier numeric conversion accepted NaN. Corrupt coefficients could produce non-finite probabilities and silently select allow. Validation was added at loading, scoring and policy selection.

Keyed audit signatures, cross-process serving state and checksum-backed artifact releases remain follow-ups in the exception list.

EXHIBIT 11

Entered into the record, plainly

The build borrows from the first-place IEEE-CIS solution: identity-key construction, card-level chargeback label semantics, group aggregates and time-consistency screening. Its unseen-client diagnosis informed investigation here, but the diagnostics do not establish unseen clients as the exclusive source of the gap. Arbiter uses causal aggregates, omits future client-mean post-processing and compares three action values under a cost scenario. Attribution and historical comparisons remain in experiments.

Identity reconstruction remains unresolved. Step-up stopping and abandonment, merchant costs, LTV and FX are assumptions; observed labels do not verify monetary outcomes. IEEE-CIS e-commerce results need fresh temporal data and merchant-specific validation before transfer to an Indian transaction mix. Current ensemble calibration, end-to-end latency, shared ordered state, keyed audit integrity and checksum-backed artifact releases remain incomplete. Component D dispute drafting was not started. The exception list records the full scope; the journal retains the build history.
